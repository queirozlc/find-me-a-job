# Research: Local ATS-Analyzer Tooling + Market Ground Truth

Scope note up front: many job boards (WeWorkRemotely, LinkedIn, hnhiring.com, Wellfound, RemoteOK's HTML pages) returned HTTP 403/410/429 to direct WebFetch — they block automated fetchers. Where I could not retrieve a raw posting, I used WebSearch result snippets, which Google/Bing index verbatim from the page; I mark those as "search-snippet quote" vs. "WebFetch-verified quote" so you know the retrieval path. I did not fabricate any posting text.

## Part A — Buildable tooling (what can run locally)

### 1. Open-source resume parsers — do they approximate a real ATS?

- **pyresparser** (OmkarPathak, spaCy+NLTK based). Extracts name, email, phone, skills, total experience, college, degree, designation, company. Search consensus: "pyresparser's extraction of education and experience are not very accurate." [pyresparser GitHub](https://github.com/OmkarPathak/pyresparser), [Eden AI overview](https://www.edenai.co/post/top-free-resume-parser-tools-apis-and-open-source-models). It's a rules+NER toy, not production-grade — good for a demo, not for scoring decisions.
- **spaCy NER approach** (custom-trained): more flexible than pyresparser but requires you to train/label your own entity model for resume-specific fields (skills, titles, dates) — spaCy's default NER doesn't know "skills" as a category. [Medium walkthrough](https://medium.com/@vikrantptl06/resume-parsing-using-spacy-af24376ec008).
- **LayoutLMv3** (Microsoft, on HuggingFace, open weights): multimodal transformer combining text + 2D layout + visual features. Needs OCR preprocessing as input (doesn't do OCR itself). Strong for token-level key-info-extraction once you have OCR'd text+boxes. [KUNGFU.AI explainer](https://www.kungfu.ai/blog-post/engineering-explained-layoutlmv3-and-the-future-of-document-ai).
- **Donut**: OCR-free, end-to-end encoder-decoder that reads the image directly and autoregressively emits structured output (can classify a doc as "resume" among invoice/receipt/form/etc.). No OCR step needed but "requires substantial fine-tuning and careful schema design" to get resume-field extraction working well — it's not resume-ready out of the box. [HF Document AI blog](https://huggingface.co/blog/document-ai), [knowledge_base survey](https://huggingface.co/datasets/John6666/knowledge_base_md_for_rag_1/blob/main/open_source_structured_document_ocr_20251115.md).
- **GROBID**: built and tuned for **scholarly/journal documents** (title, abstract, authors, affiliations, citations), F1 ~0.76–0.91 on citation-context resolution in its target domain. No resume-specific accuracy data surfaced in search — it's the wrong tool class for resumes (it assumes academic paper structure). [GROBID GitHub](https://github.com/kermitt2/grobid), citation-accuracy figure via [ResearchGate table](https://www.researchgate.net/figure/Micro-average-accuracy-for-GROBID-and-OCR-for-different-publishing-styles_tbl2_308412564).
- **Apache Tika**: general-purpose text/metadata extraction across 1000+ file types (has a GROBID integration point, `GrobidJournalParser`, via [TIKA-1699](https://issues.apache.org/jira/browse/TIKA-1699)). It's a raw-text extractor, not a field parser — you'd still need spaCy/regex/LLM logic on top. [Tika+spaCy resume walkthrough](https://medium.com/@gurvgupta/extract-information-from-resume-with-tika-and-spacy-1b5efc9f2ff).
- **pdfplumber / PyMuPDF / python-docx**: not covered in dedicated search results here, but these are the standard low-level text/layout extraction libraries underneath nearly all the above pipelines — they give you text + coordinates, not semantics.
- **Affinda**: the commercial parser is closed, but Affinda publishes a **self-hosted** container (`affinda/self-hosted` on GitHub) and client SDKs — self-hosted means "run their model locally," not "open-source model weights." [Affinda self-hosted repo](https://github.com/affinda/self-hosted), [Affinda open-source blog post](https://www.affinda.com/blog/open-source-software/).

**Honest assessment**: None of these approximate a commercial ATS (Workday/Taleo/iCIMS) end-to-end out of the box. The realistic local stack is: PyMuPDF/pdfplumber for text+layout → LayoutLMv3 (if you OCR) or a fine-tuned Donut (if you don't) for field extraction → your own scoring logic on top. Off-the-shelf pyresparser/spaCy-NER is a weekend-project quality bar, not production.

### 2. Free/open skill taxonomies — actual endpoints and licenses

- **ESCO** (EU): web-service API (machine-to-machine) + downloadable "ESCO Local API" + flat-file dumps. Key files: `skills_en` (full skills list), `languageSkillsCollection`, `skillGroups`, `skillsHierarchy`, `broaderRelationsSkillPillar`, `skillSkillRelations`. License: **EUPL 1.2** for the API itself; **Apache 2.0** for bundled components (SOLR, Fuseki, Tomcat, Spring). [ESCO API use page](https://esco.ec.europa.eu/en/use-esco/use-esco-services-api), [downloadable datasets structure](https://esco.ec.europa.eu/en/structure-esco-downloadable-datasets).
- **O*NET** (US Dept. of Labor): full downloadable database (Skills, Knowledge, Abilities, Work Activities taxonomies from the O*NET Content Model), updated quarterly. License: **CC BY 4.0**. [O*NET database](https://www.onetcenter.org/database.html), [Skills data dictionary, CC BY 4.0](https://www.onetcenter.org/dictionary/24.2/excel/skills.html).
- **Lightcast Open Skills**: free tier gives you the Skills + Titles taxonomies via a "limited, personal, royalty-free, fully paid-up, perpetual, non-transferable, non-sublicensable, worldwide" license per their terms PDF; full API access is now **contract-based** (paid), not fully free/self-serve anymore. [Lightcast Open Terms of Use PDF](https://lightcast.io/downloads/lightcast-open-skills-license-agreement-11-2023.pdf), [Open Skills access page](https://lightcast.io/open-skills/access), [Skills API docs](https://docs.lightcast.dev/apis/skills). Uncertain: I did not verify current 2026 pricing/rate limits for the free tier — the access page implies gating that search snippets didn't fully resolve.
- **EURES**: not independently verified in this pass — I did not find a direct download/API endpoint reference in the searches run. Flagging as **not observed**, don't cite it as confirmed.

### 3. Open-source ATS products — what their internals actually reveal

- **OpenCATS**: full SQL schema public at [`db/cats_schema.sql`](https://github.com/opencats/OpenCATS/blob/master/db/cats_schema.sql). Search does full-text conversion of HTML/RTF/PDF/DOC to plain text, then string search over that text (Sphinx full-text indexing was added for scale). Notably, **resume parsing capability was present, then lost, then re-added** over the project's history — current docs describe it extracting contact details and skills from PDF/Word uploads, but multiple sources note this has been unreliable across versions. [OpenCATS docs](https://opencats-documentation.readthedocs.io/en/latest/introduction.html), [forum thread on resume indexing](https://forums.opencats.org/viewtopic.php?t=223). Bottom line: it's **keyword/full-text search over converted plain text**, not semantic matching — a fairly literal confirmation of the "ATS just does string search" mental model, at least for this specific open product.
- **CandidATS**: a fork/continuation of the old CATS codebase (pre-OpenCATS fork lineage), same four-module structure (candidates/companies/contacts/job orders). [tamilamuthan/candidats](https://github.com/tamilamuthan/candidats). Doesn't add semantic matching beyond OpenCATS' lineage.
- **Odoo Recruitment**: Kanban-pipeline based, not a résumé-matching engine at all — it's a workflow/CRM tool for tracking applicants through stages, with no visible scoring/matching logic in the docs I retrieved. [Odoo 16 Recruitment docs](https://www.odoo.com/documentation/16.0/applications/hr/recruitment.html), [source](https://github.com/maestrano/odoo/blob/master/addons/hr_recruitment/hr_recruitment.py). This confirms: real ATS products are often primarily **pipeline/workflow tools**, and "matching" is frequently bolted-on or absent, not a sophisticated core algorithm.

### 4. GitHub "ATS score" checkers — real or theater?

Sampled three current repos:

- **hugounoclaw/ats-checker**: client-side only, "runs entirely in the browser, nothing uploaded," 0–100 score from "parsing structure, keyword density, action verbs, and measurable impact." [repo](https://github.com/hugounoclaw/ats-checker)
- **sunnypatell/ats-screener**: WebFetch-verified. Explicitly simulates **6 named platforms** (Workday, Taleo, iCIMS, Greenhouse, Lever, SuccessFactors) with per-platform weighting profiles (e.g., Workday = "Exact + HiredScore AI," iCIMS = "Semantic (ML-based), most forgiving"). Architecture: client-side parse → Gemini Flash Lite → 6 platform scores. **Critical disclaimer in its own README**: "All scoring simulations are approximations based on publicly available documentation, community reports, and general industry knowledge. They do not reflect the actual proprietary algorithms of any platform" and it is "not affiliated with or endorsed by" any vendor. [repo](https://github.com/sunnypatell/ats-screener) — this is the most honest of the bunch precisely because it admits it's guessing.
- **srbhr/Resume-Matcher**: WebFetch-verified. FastAPI + Next.js/React/TypeScript, TinyDB storage, runs via Docker or locally, supports 100+ LLMs including **local Ollama** (so genuinely runnable offline). Scoring is LLM-driven ("AI-generated improvements," "Resume Scoring & Keyword Highlighting") rather than a fixed deterministic algorithm — README doesn't document an embedding/similarity method. [repo](https://github.com/srbhr/Resume-Matcher)

**Honest assessment**: These tools are **heuristic keyword/LLM-judgment engines dressed as ATS simulators**, not reverse-engineered replicas of Workday/Taleo/iCIMS. The most reputable projects (ats-screener) say so explicitly in their own docs. Reddit/community consensus, aggregated by a third-party blog: "There is no real ATS score — no applicant tracking system produces a 0–100 rating of your resume. The 'ATS score' that everyone argues about comes from the checker tool, not the employer's software," and the genuinely useful checks reduce to "boring and universal: single column, plain-text name up top, standard headings, no tables for layout." [ATS Verification blog, summarizing Reddit discourse](https://atsverification.com/blog/ats-resume-questions-reddit/). For a local build, the honest framing is: build a keyword/skill-overlap + formatting-lint tool, and don't market it as "this is what Workday sees."

### 5. Commercial free tools — what each actually measures

- **Jobscan**: parses resume + JD, reports a **match rate %** against hard skills/titles/education terms; recommends ~80% as a target. Documented criticism: "there doesn't seem to be a coherent pattern to what the algorithm considers a keyword," it is explicitly **not** an ATS simulation ("real ATS work nothing like Jobscan" — hiring-manager comment cited in a review), and "an ATS doesn't score your resume on a 100-point scale and auto-reject below a threshold — that's a myth Jobscan's own marketing accidentally reinforces." [what match rate to aim for](https://www.jobscan.co/blog/what-jobscan-match-rate-should-i-aim-for/), [Medium review](https://medium.com/@chester_95184/jobscan-review-and-alternatives-2026-a300a0b54efd), [Wobo review](https://www.wobo.ai/blog/jobscan-review).
- **Resume Worded**: a **weighted composite** score (not a simple average) across three buckets — (1) brevity/wording/style (length, bullet length, filler words, buzzwords, passive voice, personal pronouns, spelling), (2) growth/leadership signals (evidence of leadership, teamwork, communication, analytical skill, drive), (3) ATS/formatting (file readability, date formats, punctuation consistency, page density, section structure, contact details). Adjusts expectations by seniority level. [How is my score calculated](https://help.resumeworded.com/article/33-how-is-my-score-calculated), [Score guide](https://resumeworded.com/score-guide). This is a **writing-quality + formatting linter**, not a JD-match tool.
- **Enhancv**: score is based on "the percentage of parsed content" (i.e., how much of the resume its own parser successfully understood — a proxy for ATS parseability) plus content-quality checks (typos, measurable accomplishments, writing caliber) that real ATS software doesn't perform. Their own copy admits: "There's no such thing as an ATS score — no tool online... gives an actual score. Rather, Enhancv's score is designed to simulate." [Enhancv resume checker](https://enhancv.com/resources/resume-checker/), [Busting ATS Myths post](https://enhancv.com/blog/busting-ats-myths/).
- **Teal**: not independently verified in this search pass beyond aggregator mentions — flagging as **not observed** rather than guessing at its methodology.

**Cross-cutting finding**: every vendor whose own docs I could read (Jobscan critics, Enhancv, ats-screener) either gets called out for it or self-admits: **the "ATS score" concept is a UX fiction**. The three real, separable signals worth building locally are (a) parseability/formatting (single-column, no tables, standard section headers, machine-readable fonts), (b) keyword/skill overlap against a JD, (c) writing-quality linting (passive voice, filler, quantified impact). None of the free tools do more than a blend of those three, dressed up with a fake precision number.

**Search-snippet, "Relevant" company listing via hnhiring index**: stack explicitly listed as "**Rails, Typescript, React, and GraphQL**" — i.e., a real current employer running Rails backend + TS/React frontend in the same shop, not treating them as mutually exclusive. [hnhiring.com](https://hnhiring.com/technologies/rails)

**Search-snippet, another listing via same index**: stack "Next.js, React, TypeScript, Ruby on Rails," requiring "**4+ years shipping production web apps**" and candidates "**comfortable [across] Rails backend and React frontend**" skills — i.e., this employer wants Rails+TS/React fluency in the *same person*, treating them as complementary, not as a stack switch.

**Synthesis** (my own read of the above, clearly marked as synthesis): the real signal from these fragments is that **companies hiring in this space are not asking "are you Rails or are you Node" — they're asking for people fluent across both**, especially where React is the frontend regardless of backend language. This cuts against a narrative of "Rails is legacy, must fully retrain" and supports a narrative of "Rails + TS/React fluency is a hireable combination on its own," at least for the handful of listings retrieved. I did **not** find a hiring manager explicitly saying "we discount Rails-background candidates" or the reverse — I found only positive/neutral mixed-stack signals and one forum comment about Rails specialists commanding higher rates due to scarcity. I could not find dedicated "hiring manager skeptical of Rails->Node candidates" commentary despite two targeted searches — this specific negative framing may not exist in visible form, or my search terms didn't surface it. Flagging as **unresolved**, not confirmed absent.

## Bottom-line recommendations for building a local ATS analyzer

1. **Parsing layer**: PyMuPDF/pdfplumber for text+layout extraction (stdlib-adjacent, no ML needed) is the pragmatic local starting point; only reach for LayoutLMv3/Donut if you need to handle scanned/image PDFs or complex multi-column layouts — both need real engineering investment (OCR pipeline or fine-tuning) before they beat plain text extraction.
2. **Skill taxonomy**: O*NET (CC BY 4.0, fully free, quarterly-updated download) is the least-encumbered option for a US-facing tool; ESCO (EUPL 1.2) if EU-facing; Lightcast now gates full API access behind a contract, so don't plan around it being free at scale.
3. **Scoring**: build three separable, honestly-labeled signals — formatting/parseability lint, keyword/skill overlap vs. a JD, and writing-quality checks — and do **not** present a single fake 0-100 "ATS score," per the near-universal finding (including from the tools' own documentation) that no real ATS produces one.
4. **Go-to-market framing for the candidate**: the retrieved LatAm-remote job market data leans Node+TypeScript+React as the default hireable combination, with Go as a secondary/bonus skill in this segment specifically (not confirmed as a general market-wide pattern — only observed in the handful of LatAm-facing postings retrieved here). Rails background paired with TS/React fluency appeared as a genuinely wanted combination in at least two real postings, not a liability.
