# How Real ATS Parse and Store Resumes — Technical Research Report

Source tiers used throughout: **[VENDOR-DOC]** = primary technical/API documentation from the company itself. **[VENDOR-MKT]** = vendor marketing/blog claim, not technical spec. **[3P-BLOG]** = third-party blog, SEO content, or "resume optimizer" site (unverified, often speculative or circular-sourced). **[PRIMARY-EVIDENCE]** = independent test data or a bug tracker / standards body artifact. Every claim below is tagged.

---

## 1. The parsing pipeline (general architecture)

No ATS vendor publishes a full internal pipeline diagram. What is directly documented:

- **File ingest**: Textkernel's Parser API accepts a document as `multipart/form-data` binary or base64 over SOAP; it does not publicly document accepted formats or OCR internals in its Quick Start guide — that detail is deferred to a separate "Sourcebox API Reference" not indexed by search **[VENDOR-DOC]** (developer.textkernel.com/Parser/master/quickstart/, fetched 2026-09-01).
- **Output data model**: Textkernel's documented model has 8 top-level sections — Document Metadata, Summary Profile, Contact Details, Education, Employment History, Skills (IT/Language/Soft/Professional), Certifications, Additional Info — each with typed sub-fields (e.g., ISO 639-1 language codes, ISO 5218 gender codes, a "Partial Extraction Indicator" flag for over-length documents) **[VENDOR-DOC]** (developer.textkernel.com/Parser/master/data_model/candidate-data-model/, fetched 2026-09-01). This is the only vendor that documents its output schema in this level of structural detail among those checked.
- **Workday**: its own admin documentation states only that "resume parsing populates fields from a resume," explicitly does **not** auto-fill Languages/Skills fields, and warns "resume parsing results can vary based on resume format and order of words" and recommends resumes "that don't have images or image-based styles." **No OCR, pipeline-stage, or algorithm detail is disclosed** **[VENDOR-DOC]** (doc.workday.com admin guide, fetched 2026-09-01). A widely repeated third-party claim that Workday runs a "two-stage system: document ingestion (strip layout) → entity extraction" could **not** be traced to any Workday-published source — treat as **unverified / not observable**.
- **SAP SuccessFactors**: official support note states "PDF documents that were scanned in or were previously images will not parse as expected, but a PDF that was previously a text document will parse as designed," and "Resume Parsing does not work 100% when Mobile Apply is enabled" **[VENDOR-DOC]** (SAP support note 2081576 / help.sap.com, via search, 2026-09-01). This confirms: no OCR fallback for image-only PDFs.

**General pipeline as reconstructed from documented fragments** (not any single vendor's authoritative diagram): (1) file-type detection → (2) text extraction (native text layer for DOCX/text-PDF; no evidence any major ATS-embedded parser does OCR on image PDFs — SAP explicitly says it does not) → (3) layout/reading-order reconstruction (undocumented algorithm, all vendors are silent on this) → (4) section segmentation via heading detection → (5) named-entity extraction (NLP/ML models, per Textkernel and Sovren "AI and machine learning" marketing language) → (6) normalization to taxonomy (skills, job titles, education levels — Textkernel and Workday both map to internal taxonomies: Textkernel taxonomy/ONET2019/ISCO2008; Workday Skills Cloud) → (7) structured JSON/XML output.

## 4. Concrete parse-breaking constructs, with evidence

| Construct | Evidence | Tier |
|---|---|---|
| **Multi-column layouts** | Jobscan's own testing: "when an ATS encountered a multi-column resume, it picked up the work experience section but ignored everything else — no skills, no 'About' section, no contact info." Mechanism stated: most parsers read a document "as a continuous, linear stream of text... left to right and top to bottom," so a 2D grid gets flattened incorrectly. | **[PRIMARY-EVIDENCE]**-adjacent (vendor's own product-testing claim, not an independent audit) — jobscan.co/blog/resume-tables-columns-ats/, 2026-09-01 |
| **Tables** | Same Jobscan source: tables used for skills or multi-role tenure get read "straight across the page, mashing unrelated sentences together into an unreadable block." | Same as above |
| **Text boxes** | Jobscan's own scanner explicitly flags "tables, text boxes, headers, footers, and graphics for removal" as parse risks. No independent quantified failure rate found. | **[VENDOR-MKT]**-adjacent product description |
| **Images of text / outlined (vectorized) text (Canva-style PDFs)** | When Canva exports certain templates, text can be rasterized or grouped as vector shapes rather than selectable characters; "if your text isn't selectable, the ATS reads a blank page." Verification method given: select-all + copy into a plain text editor — garbled/missing output predicts parser failure. | **[3P-BLOG]**, multiple concordant sources (medium.com, loopcv.pro, resumefast.io, 2026-09-01) — plausible and mechanistically sound (PDF text layer absence is a real, checkable property) but not lab-tested by a named, credible auditor. |
| **Ligatures (fi/fl/ff) dropped or nulled** | Documented, reproducible software bug: PyPDF2/pypdf issue #1351 shows `page.extract_text()` returning missing characters for 'fi'/'fl'/'ff' glyphs; root cause per multiple concordant bug reports (Apache PDFBox JIRA, Mozilla Bugzilla #1810914) is an incorrect or absent `ToUnicode` CMap mapping the ligature glyph ID back to its constituent characters, so text extractors emit `\x00` or nothing. Real resume-relevant words affected: "office," "profile," "efficient," "conflict." | **[PRIMARY-EVIDENCE]** — github.com/py-pdf/pypdf/issues/1351 (fetched 2026-09-01); corroborating Apache PDFBox and Mozilla bug trackers found via search. This is a genuine, code-level, reproducible root cause — not speculation. |
| **Icons for contact info (phone/email/LinkedIn glyphs)** | Icons rendered as images (PNG/JPEG/glyph shapes) carry no extractable text; a phone number placed after an icon with no text label can lose its semantic context and fail to be classified as a phone field. If the icon font isn't embedded/standard, extractors can assign an arbitrary substitute character to the glyph. | **[3P-BLOG]**, concordant across multiple sources (jobscan.co, rezi.ai, hireflow.net, 2026-09-01) — mechanistically consistent with the ligature/CMap bug class above (both are glyph-to-Unicode mapping failures), so credible, but no vendor-published test data. |
| **Non-standard section headings** | No independently tested dataset found; multiple sources assert generically that parsers use heading-keyword matching (e.g., "Experience," "Education") and that unconventional headings (e.g., "My Journey," "Where I've Been") reduce section-segmentation accuracy. **This specific claim is plausible but unverified by primary evidence in this research pass.** | **[3P-BLOG]**, weak — general/circular sourcing |
| **Image-only / scanned PDFs** | SAP's own support note is the strongest evidence here: "PDF documents that were scanned in or were previously images will not parse as expected." | **[VENDOR-DOC]** — confirms no OCR fallback in SuccessFactors' resume-parsing path. |
| **Header/footer placement** | Asserted by multiple ATS-optimization blogs to be skipped or misread by some parsers (e.g., contact info placed in a document header/footer region parsed by DOCX/PDF readers as a separate stream); **no primary-vendor or reproducible technical source found** confirming this mechanism specifically for resumes. | **[3P-BLOG]**, unverified |
| **Embedded/non-standard fonts** | Same CMap/glyph-mapping mechanism as the ligature bug: if a font isn't embedded or its encoding is nonstandard, extracted characters can be substituted or dropped. This is the same root cause class documented in the pypdf/PDFBox bug trackers above, generalized. | Mechanism **[PRIMARY-EVIDENCE]**-grounded (via the ligature bug), application-to-fonts-generally is **[3P-BLOG]** extrapolation |
| **Independent multi-template test (36 résumé templates through Textkernel/Tx API)** | Resumap ran 36 distinct templates with an identical fictional candidate profile through Textkernel's live API (the engine behind SuccessFactors and iCIMS). Result: **all 36 parsed without crashing**; 10/10 job-critical skills retained on 36/36 templates; median 68 distinct skills extracted (range 54–69); contact info + education fully extracted on 31/36. The only failures were **work-history segmentation**: 5/36 templates merged or incorrectly split job entries (e.g., 3 jobs collapsed into 1, or 3 jobs split into 5) — confirmed as a genuine parser limitation, not a document defect, by checking the raw PDF text layer. Notably: **the study did not isolate which specific layout construct (columns/tables/etc.) caused the segmentation errors** — it reports outcome, not cause. | **[PRIMARY-EVIDENCE]** — direct, methodologically described, reproducible-in-principle test — resumap.io/articles/textkernel-parsing-test, fetched 2026-09-01. This is the single strongest piece of quantified evidence found in this research pass. |

**Overall evidence-quality note**: the "hard" technical failure modes with reproducible, code-level evidence are the **ligature/CMap glyph-mapping bug** and the **Textkernel 36-template segmentation test**. Most other commonly repeated claims (columns, tables, icons, headers/footers, non-standard headings) are mechanistically plausible and repeated with high consensus across "resume optimizer" content sites, but those sites largely cite each other rather than a named, reproducible test — they should be treated as **credible folk-engineering knowledge, not verified fact**.

## 5. Format guidance: evidence-based vs. myth

| Claim | Status | Evidence |
|---|---|---|
| **"ATS automatically rejects 75% of resumes"** | **MYTH** | Traced to a **2012 sales pitch by Preptel**, a resume-optimization vendor that went out of business in 2013; "no research methodology was ever published to verify this claim." Career consultant Christine Assaf is quoted concluding "the statistic was created without any study, survey, or context." The number drifts (70/75/88%) across sites that repeat it, itself a signature of an unsourced viral stat. **[3P-BLOG, but well-sourced investigative piece]** (blog.theinterviewguys.com/ats-resume-rejection-myth/, fetched 2026-09-01). A companion claim — that a follow-up survey found "92% of recruiters manually review applications... using filters only to prioritize, not eliminate," and that only 8% (2/25 surveyed) configure hard content-based auto-rejection — appeared in search results attributed to HR.com, **but the source page returned HTTP 403 and could not be directly verified**; this figure is reported here as **unverified / could not confirm primary source**, not as a checked fact. |
| **"White/invisible-color text keyword stuffing works"** | **MYTH, and can actively backfire** | Multiple sources concur on the mechanism: many ATS platforms display the *full extracted text* on a candidate profile page visible to the recruiter, so hidden white text becomes visible there, not truly hidden; a recruiter who does select-all/copy on the resume also sees it directly. Consequence described: it reads as "lazy at best, dishonest at worst" and can immediately hurt a candidacy. **[3P-BLOG]**, consistent across sources (prosple.com, hrlens.io, jobscan.co, 2026-09-01) — no vendor documentation found either endorsing or specifically warning against it, but the "resume-viewer shows raw parsed text" premise is consistent with how vendor docs (e.g., Textkernel) describe outputting a full plain-text/HTML representation of the parsed document. |
| **"ATS gives resumes a score out of 100 / a match percentage"** | **MYTH as commonly framed** | No primary ATS vendor documentation found (Workday, Greenhouse, SAP, Textkernel, RChilli, Affinda) describes emitting a single 0–100 "ATS score" as a gating mechanism. The "score out of 100" concept is a product feature of **third-party resume-grading tools** (e.g., Jobscan) that simulate keyword match against a pasted job description — a distinct, separate product from the employer-side ATS itself. One source states plainly: "those scores are often invented marketing metrics, not tied to what recruiters actually see or use," and notes 56%+ of recruiters ignore or don't rely on any AI match score shown to them. **[3P-BLOG]**, self-consistent — resumeadapter.com / airesume.guru, 2026-09-01. |
| **"Avoid tables/columns/text boxes for ATS-safety"** | **EVIDENCE-BASED (mechanistically), though not universally quantified** | Grounded in the documented linear-reading-order behavior most parsers exhibit and in the concrete ligature/CMap glyph bug class (Section 4). Directionally correct advice even though a hard failure-rate number isn't available. |
| **"Avoid image-based/scanned PDFs"** | **EVIDENCE-BASED** | Directly confirmed by SAP's own support note: scanned/image PDFs "will not parse as expected" in SuccessFactors. |
| **"Simple, single-column, text-based Word or text-PDF resumes parse most reliably"** | **EVIDENCE-BASED, as the safest default** | Consistent with Workday's own guidance ("use resumes that don't have images or image-based styles"), SAP's scanned-PDF warning, and the Textkernel 36-template test (near-perfect field extraction; only structural segmentation of overlapping job entries failed). |
| **"Word-exported PDFs are more reliable than design-tool PDFs (Canva/InDesign)"** | **PLAUSIBLE / mechanistically grounded, not independently lab-tested here** | Consistent with the vector-text/rasterization issue described for Canva exports (Section 4) versus Word's native, linear text-stream PDF export. No controlled A/B test located comparing the two export pipelines' parse success rates. |

## 6. Public schemas that reveal actual structured data

- **JSON Resume** (jsonresume.org): open, community-maintained JSON schema for résumés, stable at v1.0.0 (2014, actively maintained). Explicitly scoped: "not to be the perfect description of a person but instead a description of a resume where only things relevant in the context of hiring will be allowed in." Not used by any major commercial ATS as its native storage format (no evidence found that Workday/Greenhouse/Lever/etc. consume or emit JSON Resume) — it is an independent, developer-community standard, not an ATS-adopted one. **[PRIMARY-EVIDENCE]** (docs.jsonresume.org/schema; github.com/jsonresume/resume-schema, 2026-09-01).
- **HR-XML / HR Open Standards**: HR-XML Consortium (est. 1999, California non-profit) publishes XML schemas for résumés, payroll, benefits enrollment, and staffing (Staffing 2.6 release). Its recruiting workgroup maintains a `SearchDocument` schema aimed specifically at resume-parsing interoperability. The consortium has begun publishing JSON equivalents ("HR-JSON") and is developing a new Resume/CV standard as of the most recent activity found. **Both Affinda and HireAbility explicitly document HR-XML as a supported export format**, making HR-XML the closest thing to an industry-standard resume schema actually adopted by commercial parsers. **[PRIMARY-EVIDENCE]** (hropenstandards.org; assets.noviams.com HR Open intro deck, 2026-09-01).
- **Greenhouse Harvest API** — candidate/attachment object: documented, versioned REST schema. Attachment object on create: `filename`, `type`, `content` (base64), `content_type`; on read: `filename`, `url`, `type`, `content_type`. This is the *storage/attachment* schema, not the parsed-field schema — Greenhouse's own blog confirms parsing itself is in-house and proprietary, so the *structured candidate fields* schema is not separately published in the same depth as Textkernel's. **[VENDOR-DOC]** (docs.greenhouse.io/harvest.html; github.com/grnhse/greenhouse-api-docs, 2026-09-01).
- **Lever API**: documented `Opportunity` object (pipeline/stage/status) and an array of `Resume` objects attached to it, described as carrying "parsed resume data... work history, education, and skills." The *shape* of that parsed-data object was not independently confirmed field-by-field in this pass — the search results describe it narratively, not as a field table. **[VENDOR-DOC]**, partially verified (hire.lever.co/developer/documentation, 2026-09-01).
- **Workday Candidate API**: **not located** in this research pass as a standalone, publicly browsable schema document distinct from the admin-guide page already cited; Workday's public developer/API documentation is largely gated behind customer/partner access. **Not observable** with the tools available here.
- **Textkernel candidate data model**: the most granular, fully public schema found among the named commercial parsers (Section 1/2) — effectively the closest thing to an authoritative "what fields does an enterprise-grade resume parser actually produce" reference document available without a sales contract.

## Summary of confidence

**Solid, source-verified facts**: Greenhouse's parser is in-house (not a named vendor); SAP SuccessFactors cannot OCR image-PDFs; Jobvite and Bullhorn both use DaXtra (confirmed on their own sites); SmartRecruiters and SuccessFactors use Textkernel (confirmed via press release / partner page); the ligature/CMap glyph-drop bug is a real, reproducible software defect; the "75% auto-reject" stat traces to an unsubstantiated 2012 vendor claim; JSON Resume and HR-XML are real, documented open schemas, with HR-XML actually adopted as an export format by at least two commercial parsers (Affinda, HireAbility).

**Genuinely not observable from public sources**: the exact parsing engine behind Workday, Lever, Ashby, and (definitively) iCIMS and Taleo; any independently audited, quantified failure-rate table for specific layout constructs (columns/tables/icons/headers) beyond the single Textkernel 36-template test, which measured outcomes but not per-construct causes.
